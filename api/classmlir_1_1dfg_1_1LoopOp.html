Prints a dfg::LoopOp in the custom assembly syntax consumed by parse.

If any input channel operands are present the inputs(...) clause is emitted, followed by the outputs(...) clause for output channels. Within each clause every operand is printed as value : type. The body region is always printed since a LoopOp without a region is ill-formed.

::llvm::LogicalResult verify()

Verifies that the dfg::LoopOp has a valid port mapping.

A LoopOp must monitor either all input ports of its parent ProcessOp or none of them, and likewise for output ports. Partial coverage — monitoring only a subset — is rejected to avoid ambiguity in scheduling semantics where the loop body would need to fire on an undefined subset of channels.

static ::mlir::ParseResult parse(::mlir::OpAsmParser &parser, ::mlir::OperationState &result)

Parses a dfg::LoopOp from its custom assembly syntax.

The expected syntax is: 

`dfg.loop`
  (`inputs` `(` operand-list `)`)?
  (`outputs` `(` operand-list `)`)?
  region

Unlike ProcessOp, where ports are declared as fresh block arguments, LoopOp refers to channel values already live in the enclosing process body. The inputs/outputs lists are therefore parsed as resolved operands (ssaName : type) rather than new argument declarations. The operandSegmentSizes attribute is derived from the parsed counts and stored automatically. The body region is mandatory and must be non-empty.
