# The CGRA Variant

`picea` lowers a marked loop nest onto a **STRELA CGRA** attached to an **X-HEEP RISC-V** core, emitting a C driver that programs the fabric over MMIO and runs on Verilator.
The custom work lives in the `cgra` dialect and its transformation passes.

This page is the narrative reference: what each stage is for and why it is shaped the way it is.
The exhaustive per-pass option lists are generated from the tablegen sources and live under {doc}`/Passes/CGRAPasses`; the operation definitions under {doc}`/Dialects/CGRAOps`.

## 1. Overview

The input is a C program (lowered to affine MLIR by Polygeist's `cgeist`), a quantized `linalg`-on-tensors model, or a `dfg.operator` written directly in the DFG dialect (§4).
From there:

1. The front end legalizes the datapath to 32-bit and rewrites the loop body into the operations the fabric ALU actually has (§3).
2. `--annotate-to-cgra` marks each offloadable loop nest with `cgra.deploy`, and `--outline-cgra-deploy` splits it from the host code (§4).
3. Buffers that cross a deploy boundary are given symbols and packed (§5).
4. Two branches then meet in the generated driver:
   - the **software** branch (§6) emits the STRELA MMIO application;
   - the **hardware** branch (§7) exports a data-flow graph for the elastic-cgra Gurobi mapper, which returns placement, bitstream and the IMN/OMN channel map.

Because both branches must agree on which loops went to the fabric and in what order, the passes they share are grouped into named pipelines (§8) rather than being spelled out per call site.

## 2. Dialect operations

Defined in `include/picea-mlir/Dialect/CGRA/IR/`:

| Operation | Purpose |
|---|---|
| `cgra.deploy` | Marks a loop nest for offload. Its `ins(streams)` operands make the offloaded data flow explicit. |
| `cgra.yield` | Terminator of a `cgra.deploy` region. |
| `cgra.strela_write` | A single 32-bit volatile MMIO write to a symbolically-named STRELA control register. |
| `cgra.strela_read` | The same, for a read. |

The STRELA registers are named symbolically on the ops; the concrete MMIO addresses are resolved only at `--strela-to-llvm`, so the register map lives in exactly one place.

## 3. Front-end legalization

The fabric has a narrow, straight-line, 32-bit datapath.
Four passes bring an arbitrary loop body into that form:

- `--widen-storage-to-i32` retypes i4/i8/i16 memref **storage** to i32 with load/store boundary casts.
  It runs before legalization.
- `--legalize-to-i32` rewrites narrow and i64 **arithmetic** into i32 sequences, preserving results exactly.
  `--legalize-to-i32-func` is the single-function variant.
- `--predicated-store-to-select` turns a predicated `affine.store` into an `arith.select`, removing control flow from the body.
- `--normalize-cgra-compare` folds every predicate into an expression on the operand, because the compare FU tests against zero and realizes only `>0` and `==0`.

  The sign-bit-flip identity used for unsigned compares, and the `+1` used for `<=`/`>=`, both assume no wraparound at the integer extremes.
- `--expand-fabric-ops` expands div/rem by a power of two and the integer `math` intrinsics into fabric ALU sequences.

`--annotate-to-cgra` treats a loop containing an operation that no CGRA transform can lower to a fabric operation (float, integer divide/remainder, `math`, `call`) as a hard error rather than silently keeping it on the host.
The classification lives in `cgra::classifyFabricOp` (`Transforms/CGRAAnalysisUtils.h`).

## 4. Marking, outlining and dispatch

- `--annotate-to-cgra` wraps each offloadable outermost loop in `cgra.deploy`.
- `--outline-cgra-deploy` splits the kernel from the host code into `<H>_init` / `<H>_kernel` / `<H>_post`.
  A bare kernel is outlined too under `drop-host`.
- `--annotate-dispatch-io` classifies each stream as input, output or inout and stamps `dispatch_size`.
- `--prune-to-entry=entry=<H>` privatizes everything outside `<H>`'s outlined family so `symbol-dce` drops it — chiefly a hand-written CPU reference, which `--annotate-to-cgra` would otherwise have offloaded too. It reads the `cgra.outlined_from` stamp the outliner leaves, so one name replaces the thousand-entry exclude list this used to need.

Supporting rewrites that reshape a nest into something offloadable at all: `--promote-accumulator`, `--split-reduction-bias`, `--promote-scalar-reduction` (§8), `--fuse-cgra-nests`, `--unroll-lanes`, `--partition-cgra-dfg`, `--conv-to-im2col`, `--expand-memref-copy`, `--hoist-reduction-unpack`, `--strip-stage-prints`.

`--dfg-operator-to-cgra` bridges the DFG dialect to this path.
A self-contained `dfg.operator` is an SDF actor whose body is ordinary compute, which is exactly a function: its **input ports become the arguments** and the values handed to `dfg.output` become the **results**, so the actor is handed back to `func.func` and the rest of the pipeline compiles it unchanged.
A multi-actor graph wired with `dfg.channel`/`push`/`pull` is out of scope and left alone.

A **wired graph** — a `dfg.region` of `dfg.channel` edges and `dfg.instantiate` nodes, which is what the MYRTUS DPE emits for a quantized network — is flattened the same way: the region becomes a `func.func` calling its actors in topological order with each channel threaded as an SSA value, and `--inline` then folds it into one function.
A multi-actor graph wired with `dfg.push`/`dfg.pull` (a KPN process firing on a stream) is out of scope and left alone.

There are three ways in.
The MYRTUS networks reach it as a *round trip* — `--convert-func-to-dfg` wraps their `@main` in an actor and this pass immediately unwraps it, leaving the lowered and annotated IR byte-identical, which is what proves the bridge is lossless.
Two models instead **start** there, their source file being the DFG IR itself:
`src/models/dfg_blend` (one self-contained actor; whole chain to a Verilator `SUCCESS` in about two minutes) and `src/models/myrtus_dfg` (a real MYRTUS SDF graph — 4 actors across 2 conv layers, 20 fabric configurations, 5.32x, `SUCCESS` with the x86 golden matching).
Both are written up under `docs/DFG/`, with every intermediate artifact and the device logs.

## 5. Buffer placement

- `--promote-alloca-to-global` gives a stack-allocated buffer static storage.
  It belongs to the **pre**-annotate phase: it must run before the nests are wrapped.
- `--promote-shared-buffers` gives every cross-deploy buffer a symbol.
- `--pack-cgra-buffers` shares storage between intermediates whose live ranges do not overlap.

## 6. Driver generation (software branch)

The driver and its dataset are **translations**, not passes: they generate an
artifact out of the IR instead of rewriting it, so they live in `lib/Target/`
and run under `picea-translate`, not `picea-opt`.

```
picea-translate --cgra-to-driver  <opts> kernel.mlir -o main.c
picea-translate --cgra-to-dataset <opts> kernel.mlir -o dataset.h
```

A GR-HEEP / X-HEEP STRELA application is two files, and `mlir-translate` gives
a translation exactly one output stream, so each artifact is its own
translation over one shared analysis. Both take the **same** options; run both
over the same input to get a complete application.

Which of two emitters runs is a property of the IR, not an option:

- **single-deploy**, chosen when the streams are function arguments.
  It declares the arrays, calls the outlined `<base>_init` and `_post`, programs and starts the fabric, then waits on the interrupt.
- **multi-config**, chosen when the streams are module-level `memref.global`.
  It emits one configuration per deploy, run consecutively and in place.

Either way the streams and dispatch metadata come from the IR, and the result is checked against a reference transliterated from the deploy loops.

A **heterogeneous** whole-model driver is also supported: fabric configurations for the streamable nests, CPU code for the convolutions and reductions that stay on the host, and a buffer registry threading arrays between them.

Options, all carrying a `cgra-` prefix because a translation's options are
global flags on `picea-translate` rather than scoped to a pass:
`--cgra-iomap`, `--cgra-iomap-prefix`, `--cgra-bitstream-sym`,
`--cgra-bitstream-header`, `--cgra-name`, `--cgra-sim`,
`--cgra-hoist-descriptors`, `--cgra-watch-buffers`, `--cgra-ck-only`,
`--cgra-no-deployed-metric`, `--cgra-x86-golden`, `--cgra-max-dispatch`,
`--cgra-interleaved-kb`, `--cgra-progress-every`, `--cgra-no-reference`.
The old `output=` option is gone: the output path is `picea-translate`'s own
`-o`.

Lowering to the actual MMIO sequence is two further passes, which *do* rewrite the IR and so remain in `picea-opt`:

- `--cgra-deploy-to-strela` turns each `cgra.deploy` into the `strela_write` and `strela_read` programming sequence, optionally permuted by the mapper's `io_map.json`.
- `--strela-to-llvm` turns the `strela_*` ops into volatile `llvm.load` and `llvm.store` at the resolved MMIO addresses.

## 7. DFG export (hardware branch)

`picea-translate --cgra-to-dot` writes one GraphViz `.dot` per fabric-streamable loop for the elastic-cgra ILP mapper: FU nodes for arith, shift, logical, select and compare; width casts are pass-through; `shrui` is corrected for the fabric's arithmetic-only right shift.

```
picea-opt --legalize-fabric-body kernel.mlir \
  | picea-translate --cgra-to-dot --output-dir=dfg -o /dev/null
```

This is the one translation that does **not** put its payload on `-o`. It emits
a numbered *set* of files, `loop_<NN>_iter<lb>to<ub>.dot`, whose names are
load-bearing — the mapper pairs bitstream *k* with the driver's configuration
*k*. So the graphs go to `--output-dir` and `-o` receives the manifest, one
filename per line. Nothing is written unless every exported loop verifies, so a
failure can never leave a partial — and therefore misnumbered — set behind.

An unexpanded operation reaching this translation is a **hard error**, not a warning: the shipped DFG-export rules discard its output, so a warning would be thrown away and the mapper would silently receive an incomplete graph.

## 8. Pipelines

Declared in `include/picea-mlir/Conversion/ConvertToCGRA/ConvertToCGRA.h` and registered by `picea::registerConvertToCGRAPipelines()`.

| Flag | Passes |
|---|---|
| `--convert-to-cgra` | the whole uniform front end (below) |
| `--legalize-fabric-body` | `predicated-store-to-select` → `normalize-cgra-compare` → `expand-fabric-ops` |
| `--shape-cgra-reductions` | `promote-accumulator` → `split-reduction-bias` → `promote-scalar-reduction` |
| `--place-cgra-buffers` | `promote-shared-buffers` → `pack-cgra-buffers` |
| `--cgra-deploy-to-llvm` | `cgra-deploy-to-strela` → `strela-to-llvm` |

`--legalize-fabric-body` is a **correctness** device, not tidiness.
Those three passes must run before `--annotate-to-cgra` (which decides fabric-vs-CPU) *and* before `--export-loop-dfg` (which emits the `.dot` for the loops annotate chose).
If the two sites ever diverge, the driver's configuration indices and the mapper's bitstream indices silently stop matching.
One flag makes them identical by construction.

`--shape-cgra-reductions` has a real **order** dependency.
The fabric accumulator is an FU that starts from zero and is fed by a load-accumulate-store nest, and the three passes converge on that single invariant from different directions: `promote-accumulator` may leave a `C = 1*C + reduce` seed that only `split-reduction-bias` can make zero-seeded (`isFabricStreamable` then keeps any survivor on the CPU), while `promote-scalar-reduction` handles the opposite shape, a top-level scalar `iter_args` nest that stores nothing.

`--place-cgra-buffers` is deliberately only the two post-annotation passes; `--promote-alloca-to-global` cannot join the group because it has to run before the nests are wrapped.

`--convert-to-cgra` is the **uniform front end**: everything a kernel runs, in the one order that works, assembled from the groupings above rather than respelling them.

```
--inline → --conv-to-im2col → [--hoist-reduction-unpack] → --promote-alloca-to-global
  → --shape-cgra-reductions → --fuse-cgra-nests → --legalize-fabric-body
  → --partition-cgra-dfg → --annotate-to-cgra → --place-cgra-buffers
  → --outline-cgra-deploy=drop-host → --annotate-dispatch-io
```

Options: `max-fus` (default 14), `max-outs` (3), `hoist-reduction-unpack` (on), `entry` (none).

Pass `entry=<host function>` whenever the source carries a CPU reference implementation: without it the export emits a `.dot` for the reference's loops too, and the mapper then numbers bitstreams over a larger set than the driver numbers configurations — `tfm_gemver` gives 4 graphs instead of 1. See `--prune-to-entry` (§4).

`promote-shared-buffers` runs **once**, inside `--place-cgra-buffers`. `src/Makefile` used to run it a second time immediately before that grouping; the duplicate was accidental and provably inert, and is not reproduced here.

`--symbol-privatize` / `--symbol-dce` stay outside the pipeline: their exclude list is per-kernel.

The equivalence between this flag and the explicit sequence is what
`test/Conversion/convert-to-cgra.mlir` checks, by diffing the two. That matters
because the DFG export feeds the mapper while the driver numbers its
configurations from the same front end — if the two spellings ever diverge, the
bitstream and configuration indices stop matching, silently.

## 9. Driving it with `resin`

`resin` is the compiler driver: it dispatches to `picea-opt` and
`picea-translate` so a whole artifact set comes out of one command. The CGRA
path is **two** sub-flows, not one, because the place-and-route step between
them is a Gurobi ILP living in `src/elastic-cgra` — outside the compiler, and
outside `resin`.

```
                      resin --cgra-dfg
kernel.mlir ──────────────────────────────> out/cgra.mlir
                                            out/dfg/loop_<NN>_*.dot
                                            out/dfg/manifest.txt
                                                    │
                                   [ elastic-cgra mapper, Gurobi ]
                                                    │
                                            <K>_<N>_io_map.json
                                            <K>_<N>_kernel.h
                                                    │
                      resin --cgra-driver           ▼
out/cgra.mlir ─────────────────────────────> out/app/main.c
                                             out/app/dataset.h
```

```bash
resin --cgra-dfg -p 'convert-to-cgra=max-fus=11 entry=main' -o out kernel.mlir
# ... run the mapper over out/dfg ...
resin --cgra-driver -o out out/cgra.mlir -- \
  --cgra-name=k --cgra-iomap-prefix=out/k_ --cgra-interleaved-kb=496
```

Everything after a bare `--` is forwarded verbatim to `picea-translate`, so
`resin` does not have to mirror the driver's fifteen options.

`--cgra-dfg` re-runs `--legalize-fabric-body` on the pipeline's output before
exporting. That is belt-and-braces — it was measured to be a no-op on all six
reference kernels — and is kept so a pass added later between `annotate` and
the export cannot quietly break the "same legalization at both sites"
guarantee that keeps configuration and bitstream indices in step.

Note `resin` is not what `src/Makefile` uses; the Makefile drives the same
tools directly because it also owns the mapper, the RISC-V build and Verilator.
`resin` is the single-command path for one kernel.
